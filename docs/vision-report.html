scribe

A publishing client for whatever you built in Pages CMS.

Vision · Architecture · System Design · UI Strategy · UX Mockups  |  for review & comment

This report lays out where scribe is going and, more importantly, how it should feel to use — especially the part that doesn't exist yet: going from "here is my Pages CMS site" to "here is my tailored editor," driven entirely through a UI. Sections are numbered so you can comment precisely ("§5.2, the field mapper…"). Mockups are deliberately drawn in scribe's own visual language so they read as real future screens, not a different product. Nothing here is built yet — it's for you to shoot holes in before we commit to workflows.

1Vision & principles

scribe is a content publishing client, not a website builder. Pages CMS already lets you define a site with any collections and fields you like. scribe sits on your repo and makes writing and managing that content a first-class experience — tuned to your shapes, never a shape it imposes.

  • Publish, don't design. No layouts, themes, templates, or type definitions. Those belong to your site and Pages CMS.
  • Accommodate the author's schema. Your .pages.yml is the contract. scribe maps onto it and never asks you to change it.
  • Preserve everything. Fields scribe has no dedicated editor for are kept verbatim and editable as raw fields. Round-trips never drop data.
  • Core + plugins, no privileged internals. Each content type's editor is a plugin built on a public SDK. scribe ships great core plugins (block post editor, tag manager) on that same SDK.
  • Forkable. "My blog uses three kinds of tags" is solved by forking a plugin, not patching scribe.
The one-sentence testAn ordinary blog gets a beautiful post + tag editor out of the box; a bespoke site maps its types in a UI and forks a plugin when it wants something custom. Same tool, any site.

2The core problem: schema → editor

The hard, interesting problem is the seam between an arbitrary Pages CMS schema and a focused editing experience. A blog-post editor wants a small, known content model — a title, a date, a body, maybe tags. A real site's collection has those plus whatever else the author dreamed up. scribe has to bind the known fields and gracefully carry the rest.

Every field on a collection lands in one of three buckets. This is the heart of the whole product:

AMapped · requiredThe experience cannot run without these (title, date, body). Must bind to a real field. Validated.
BMapped · optionalBound if your schema has them (description, tags, draft, updatedDate). Hidden if not.
CUnmapped · rawEverything bespoke (coAuthor, projectName, hasVideo…). Edited via typed widgets + a YAML escape hatch. Never lost.

Get this seam right and scribe fits any site. Get it wrong and it only ever fits one blog. That's why the setup/mapping UX (§5.1–5.2) is the most important thing to nail early.

3System architecture

Seven layers, bottom up. Today only a hardcoded slice of this exists; the roadmap (§7) builds the rest.

1SchemaParse .pages.yml → normalized collections + fields (name, type, required, list, options).
2Generic contentA resource is {collection, slug, fields:{…}, body?}. Service reads/writes any collection; unknown fields preserved.
3Experience pluginDeclares a content model (required/optional fields + roles) and renders an Editor. Core: blog-post, tag, generic.
4Mapping.scribe.yml binds a collection's fields to an experience's model. Three buckets (§2). Edited in the UI.
5Field widgetsOne widget per type (string, text, date, boolean, image, select, list, object, reference). Used by editors and the raw editor.
6Data accessHooks to list/get/save/create/delete any collection + find referencers — powers autocomplete, cross-type edits, cascades.
7Core SDK + pluginsExports the editors, widgets, hooks, contract types. Plugins (core & third-party) build only on this.

4UI strategy

  • Setup is a UI, not a config file you hand-edit. scribe auto-detects your collections from .pages.yml, proposes mappings, and lets you confirm/adjust visually. .scribe.yml is the output, not the interface.
  • Progressive disclosure. The writing surface stays clean (title + body). Mapped optional fields live in a details panel. Raw/bespoke fields live one layer deeper, behind "more fields," with a "show me only what the editor doesn't already cover" filter.
  • The editor is derived, not authored. What you see when editing a post is generated from the mapping. Change the mapping → the editor changes. No per-post layout work.
  • Confidence about data. Always make it obvious that untouched/bespoke fields are safe. A visible "raw fields preserved" affordance beats a silent guarantee.
  • Consistency with the writing room. Espresso chrome, parchment page, Fraunces/Newsreader. Setup and management screens are chrome (espresso); editing is paper.

Why a wizard, not a formThe first run is the one moment the mapping has your full attention. §5.2 · field mapper — three buckets, live validation

Decisions baked into this mockupDirection reads model ← yourField (the editor's needs on the left, your schema on the right). Required-but-missing is the only thing that blocks saving. tags is recognized as a reference to the tags collection (Pages CMS has no native reference type, so this is a scribe convention you set here). The raw bucket is shown, not hidden — you always know what's carried as-is.

6Plugin & extensibility model

An experience plugin declares a content model (the fields it needs, with roles/types) and an Editor component that renders against mapped values + a data context. It consumes only the public SDK — the same one core uses. The SDK exports the document/markdown editor, a ReferencePicker (the tag chips, generalized), field widgets, the raw editor, and the data hooks. A shared editor (e.g. tags) is one import reused across plugins.

Decision to confirmBuild-time plugins for v1. A deployment configures which plugins it uses (core, npm packages, or a local plugins/ dir) and builds. Forking = fork the package, point your build at it. This covers both goals you named — public plugin packages and local deployment — without the bundling/trust problems of loading arbitrary JS at runtime. Runtime/dynamic plugin loading stays a deferred stretch, not designed-out.

7Roadmap

Each milestone stays shippable and keeps the current posts/tags working (guarded by the markdown round-trip tests). M1 is the keystone refactor.

M1Schema-driven coreRead .pages.yml; generic resource/store/API over any collection; posts+tags keep working through it.
M2Experience contract + mappingPlugin interface; .scribe.yml + loader + validation; the setup wizard & field mapper UI (§5.1–5.2).
M3Field widgets + raw editorWidget-per-type library; the three-bucket editing surface incl. the raw editor + filter (§5.3).
M4Data access + referencesHooks to read/edit any collection; first-class reference fields; ReferencePicker.
M5Cascades & cross-editsFind referencers; cascade rename/delete with preview (§5.4); inline-edit a referenced resource.
M6Core SDK + packagingExtract the SDK; build-time plugin registration; ship core plugins on the SDK; authoring docs + example plugin.
M7Distribution + deferred infraPlugin API versioning; then staging/promote, image-upload plugin, k3s deploy, auth modes.

8Resolved decisions ✓ decided 2026-06

Q1 · Mapper direction → keep model ← yourField (editor's needs on the left). ✓
Q2 · Setup → a wizard that recommends, never auto-configures. Basic field-shape rules pre-fill guesses; every binding is an explicit confirm. No silent config. ✓
Q3 · Raw fields → present but hidden by default, behind an "advanced / show additional fields" reveal — in both the mapper and the editor. You can see everything that exists, just not by default. ✓
Q4 · References → per-field and explicit, never inferred. You declare a field as a reference in .scribe.yml. ✓
Q5 · Plugins → folder-based, loaded at startup/build. Drop plugin folders into a plugins/ dir; discovered on build/start. No hot reload, no in-UI install. Forking = copy a folder. ✓
Q6 · Cascades → on by default, with an impact preview ("this will update 26 resources") and an opt-out before applying. ✓
